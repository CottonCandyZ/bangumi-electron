# 离线 fetch 审查（2026-09-05）

审查基线：已发布的 beta.28（b0f55cc4）。以下问题来自代码路径检查；本轮行为修改仅涉及首次完整同步，未把下列问题宣称为已修复。

## 离线能力边界

已有本地收藏和章节进度可读、可编辑，修改会进入持久队列，联网后再同步。已缓存的资源可供部分页面离线显示。首次登录、未缓存的条目、远端搜索和服务器写入仍需要网络。图片等依赖 Chromium 缓存，当前没有完整离线下载或离线覆盖率保证。完整收藏同步也不等于下载整个应用的全部内容。

## 待处理发现

1. **P2：单条详情的 404 不进入可见性处理。** `local-resource.ts:54` 的单条 refresh 仅处理成功；过期 SQLite 数据先返回，后台失败在 `:26` 被吞掉。直接打开后来不存在或无权访问的详情时，旧内容继续显示，也不会写入该账号的不可见标记。批量路径则会标记和重置详情查询，两个入口语义不同。应共享成功、404、暂时故障的处理路径。

2. **P2：资源请求没有全局并发上限。** `resource-refresh.ts:24` 只保证一个批次内串行，`local-resource.ts:17` 只按完整 query key 去重。不同分类、不同 ID 集合以及单条详情可同时发请求，重叠 ID 也可能重复获取。热门网页和收藏同步的队列不能限制这里的公共 API 请求。应按资源与账号合并重复请求，再接入资源请求队列。

3. **P2：后台刷新缺少账号切换和取消边界。** `local-resource.ts:23` 使用独立定时器和 Promise，没有读取 Query 的 AbortSignal，也不在登出、切号或卸载时取消。缓存 key 和可见性标记使用创建闭包时的账号，而 `config/base.ts:79` 获取执行请求时的当前 token。切号过程中，旧批次后续请求可能使用新身份，结果却写入旧身份的可见性标记或查询。应绑定身份版本，并在请求、写入和发布结果前检查是否仍有效。

4. **P2：辅助 IndexedDB 故障阻断主缓存读取。** `local-resource.ts:70` 在读 SQLite 之前等待可见性标记；批量路径 `:122` 也逐项等待。`resource-visibility.ts` 没有错误处理，IndexedDB 打开或读取失败会使整个资源查询失败，即使 SQLite 内有可用内容。应该设计明确的降级策略，并测试元数据存储失败；不能简单忽略所有错误，以免恢复本应隐藏的条目。

## 本轮修改

首次完整同步只能由同步面板的“开始首次同步”触发。启动、重连、更新 token、单条资源读取和本地编辑只处理对应请求或待提交修改，不再因为 `listComplete` 为 false 自动下载整个收藏列表。用户启动的完整同步发生暂时故障时仍保留原有重试行为，请求并发不变。

验证：63 项收藏 Vitest 测试、完整 TypeScript 检查通过；新增用例覆盖未同步账号启动/重连不扫全量、手动开始才扫描，以及单条读取和待提交编辑不隐式扫描。

## 建议的整理方向

保留本地收藏事务与同步引擎，把通用资源刷新拆成明确的读取缓存、发起请求、处理结果三步。由 Query 管理任务生命周期，统一单条和批量的错误分类、账号边界与缓存发布；可见性元数据应使用批量读写和稳定的存储实例。先补上述行为回归，再整理结构，避免为了去掉重复代码改变离线和权限语义。
